RADAR V2 — AUTHORITATIVE POLICY
Repository: Sadikkucuk/lovable-opportunity-radar. Timezone: Europe/Istanbul.
Policy: radar-v2-no-runtime-services-20261010. Effective 10 October 2026.

PURPOSE
Discover commercially useful software from scientific, industrial and technology
news. Read prompts/RESEARCH_METHOD.txt for decomposition, novelty deltas, actors,
JTBD, product transformations and cross-article combinations. This is opportunity
research, not a news summary. Keep all distinct plausible opportunities; no Top-N.
Every assigned article needs an explicit decision. Ten articles/one candidate is
a persistence unit, never an invocation cap. Save, then continue while able.

PRODUCT POLICY
Lovable credits and domain/hosting have no evaluation ceiling; estimates are
informational and actual provider quotas still apply.
No required external API, external database service, external AI agent/model
service in the delivered product, even on a free tier or with the buyer's key.
No separate paid research API, agent, database or server for Radar itself.
Existing ChatGPT research, GitHub integration, public web reading and Lovable
code generation remain permitted. No new services, subscriptions or secrets.
Prefer deterministic logic, local/browser computation, file/CSV imports/exports,
static/downloaded data and human input. If this destroys core value, reject it.
Unknown counts/costs are null, not zero. No limit of 500 credits.
Türkiye: 0 identified direct competitors; global: at most 3, in dated documented
search scope. Direct = same customer + core job + substantially same workflow.
Explain adjacent tools separately; never claim exhaustive absence.
Business explanations are Turkish. Scope: Lüleburgaz/Türkiye/Dünya/Evren; Evren
only for actual off-Earth operations. Preserve concrete local evidence.

PERSISTENCE
Read state/v2/config.json first; work only if mode=active.
Use prompts/WORK_PROTOCOL.txt and the prompt for the assigned kind.
Only immutable job payload/source_commit is authoritative; never replace an
open job's input with rolling main, today's date or stale conversation content.
Only create claims/results and immutable worker-events. Never write catalog/history, counters, manifests,
inboxes or releases; deterministic Actions code owns these.
All 89 baseline catalog/history/site records, IDs and details remain unchanged.
New observations about an old idea belong in research receipts, not the old row.
Compare with current complete catalog/history before qualifying a new idea.
Do not restore October 3 prompts, restart legacy tasks, create recursive tasks,
or work around tool/platform approval controls.

FAILURES AND RESULTS
Try bounded alternative-source research for an inaccessible article. If proof
remains unavailable, record unverified and continue. Never relabel unknown as
qualified. Technical completion, evidence and site delivery are separate.
Verify each GitHub receipt by read-back. On timeout, inspect the path before
retrying. Transient writes may be retried at most three times with bounded delay.
Never claim unpersisted progress. Next scheduled invocation resumes unfinished
jobs, including earlier dates. Platform limits remain; no routine "devam" request.
Turkish summary: actual completed/remaining jobs and research conclusions.
An unverified validation decision is a TERMINAL IMMUTABLE OBSERVATION for
its original job, NOT completion of the underlying evidence investigation.
The controller schedules at most two linked, new evidence_followup
validation jobs for missing original-source, dated competitor, feasibility
or semantic-history checks. Do not claim that unverified plus an empty
evidence array constitutes completed competition research. Reuse still
fresh, genuinely read and supported existing evidence; older notes
are a starting point only. Use claim identity preflight and error routing
from radar/claim_guard.py; obey permissions without workarounds. Never
create recursive ad hoc Worker tasks or inflate receipt count with
zero-research placeholders. Report separately work receipts, qualified
products and unresolved evidence checks. >=20 units/session is an
aspirational throughput metric, NOT a quality override or work cap.
