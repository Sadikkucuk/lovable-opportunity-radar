
==================================================
CATALOG PRESERVATION — HARD SAFETY RULE
==================================================

The existing idea catalog is append/update-only for radar runs.

Before any catalog write:
- read the current state/idea_catalog.json;
- preserve EVERY existing idea record and canonical_key;
- a radar run may append new ideas or materially update a matching existing idea;
- a radar run must NEVER delete, truncate, replace, archive, hide or omit an existing
  catalog idea merely because it was not rediscovered today;
- never rebuild the catalog from only today's results.

For the 2026-09-28 run specifically, seven existing catalog ideas are protected.
A safety backup exists at:
state/backups/2026-09-28-idea_catalog.json

If a proposed write would reduce the catalog idea count below the count that
existed at run start, ABORT THE CATALOG WRITE and mark the run:
CATALOG_PRESERVATION_FAILED

Do not publish a completed run until the preservation check passes.

MULTI-WORKER RADAR — SINGLE ORCHESTRATOR

Repository: Sadikkucuk/lovable-opportunity-radar
Use Europe/Istanbul local date for state/runs/YYYY-MM-DD.

PURPOSE

This is the only post-discovery scheduled task. It is invoked several times
during the day. Each invocation advances EXACTLY ONE unfinished stage and then
stops. This bounds runtime while keeping the total number of active ChatGPT
automations at five.

Production tasks:
- Discovery W1
- Discovery W2
- Discovery W3
- Discovery W4
- This Orchestrator

Read:
- CHATGPT_RADAR_PROMPT.txt
- prompts/MERGE_WORKER.txt for merge semantics
- prompts/VALIDATOR_WORKER.txt for competition/evidence semantics
- prompts/FINALIZER.txt for publication semantics
- state/idea_history.json
- state/idea_catalog.json
- current day's state/runs/YYYY-MM-DD/ files

DO NOT use the current docs/batches/index.json as the completion denominator
after discovery has started. The collector refreshes hourly. Instead, the four
discovery workers must have captured the SAME immutable
source_batch_index_generated_at and source_total_items at 07:00.

==================================================
SAME-DAY SOURCE REFRESH — GENERATION-SAFE RUNS
==================================================

A source/feed regeneration can occur after today's first discovery started, especially
after sources.opml or aggregate.py changes. Never overwrite or mix an earlier frozen run.

At invocation start compare:
- current docs/batches/index.json generated_at
- the generation of today's primary run, if any
- any existing refresh run generations.

If the current index generated_at is newer than the generation already processed today,
create/use a generation-specific refresh namespace:

state/runs/YYYY-MM-DD/refresh-GENKEY/

where GENKEY is the UTC generated_at compacted as YYYYMMDDTHHMMSSZ
(example: 20260930T061311Z).

Inside that refresh namespace use the same structure:
- discovery/worker-1.json ... worker-4.json
- merge/candidates.json and merge/status.json
- validation/progress.json and validation/chunk-NNN.json
- final/report.json
- orchestrator-status.json

The refresh generation is immutable once its first worker is written. All four workers,
merge, validation and finalization MUST use that exact generation. Never mix files from
the primary daily run or another refresh generation.

When a refresh namespace is active, every path in stages 1-4 below is relative to that
refresh namespace instead of state/runs/YYYY-MM-DD/.

A completed primary daily run does NOT block a newer refresh. Stage 0 applies only when
the newest available generation has a FULL_RADAR_COMPLETE report. If a newer current
generation exists, process it as a refresh first.

Publication remains append/update-only. Refresh finalization must compare against the
current idea_history and idea_catalog, so ideas already published by the earlier same-day
run are semantically deduplicated rather than emitted twice.

Do not create a refresh merely because the hourly collector timestamp changed with no
meaningful source/config change during an active normal day. A refresh is required when
the newer generation follows a source/config change or an explicit clean-rerun request.

==================================================
STAGE SELECTION — ONE STAGE PER INVOCATION
==================================================

At the start, inspect today's run state and choose the FIRST applicable stage:

0. If final/report.json exists with overall_status="FULL_RADAR_COMPLETE":
   do nothing further. Return only: "Bugünkü radar zaten tamamlandı."

1. DISCOVERY GATE / REPAIR
2. MERGE
3. VALIDATE NEXT CHUNK
4. FINALIZE

Run exactly one of these stages per invocation.

==================================================
1. DISCOVERY GATE / REPAIR
==================================================

Expected workers and assignments:
- worker 1: batches 1-6
- worker 2: batches 7-12
- worker 3: batches 13-18
- worker 4: batches 19 through source_batch_count

Read:
state/runs/YYYY-MM-DD/discovery/worker-1.json
...
worker-4.json

A worker is acceptable only if:
- file exists
- status="complete"
- assigned batches are correct
- feed_items_triaged == feed_items_expected
- source_batch_index_generated_at exists

All four acceptable workers must have identical:
- source_batch_index_generated_at
- source_total_items
- source_batch_count

And:
sum(feed_items_triaged across workers) == source_total_items

If ONE OR MORE workers are missing/incomplete BUT every currently complete worker
shares one source_batch_index_generated_at AND the current docs/batches/index.json
still has that exact generated_at, repair EXACTLY ONE missing/incomplete worker in
this invocation using prompts/DISCOVERY_WORKER.txt and that worker's assignment.
Choose the lowest worker_id needing repair. Persist its worker JSON successfully,
then stop. A failed persistence is not a completed repair and must not disable any
worker or the orchestrator.

If the current index no longer matches the workers' captured generation, do NOT
mix generations. Write:
state/runs/YYYY-MM-DD/orchestrator-status.json

with:
status="RADAR_INPUT_MISMATCH"
and exact worker generations/coverage.

Do not publish. Stop.

If all four workers pass the gate, proceed to stage selection on the NEXT invocation
unless merge already exists. For this invocation, write/update orchestrator-status.json:
status="DISCOVERY_COMPLETE"
with:
- source_batch_index_generated_at
- feed_records_total
- feed_records_triaged
- candidate_articles_seen
- original_articles_verified
- raw_opportunity_count

Then stop.

==================================================
2. MERGE
==================================================

Run only when discovery gate is complete and
state/runs/YYYY-MM-DD/merge/status.json is absent or not complete.

Use the merge rules in prompts/MERGE_WORKER.txt, with these overrides:
- trust the frozen worker generation, not the current live feed index;
- combine all four raw ledgers;
- event-cluster syndicated/duplicate developments;
- semantic idea identity = target customer + core JTBD + product mechanism;
- run dataset-wide cross-article combination discovery;
- apply productization and zero-cost/Lovable feasibility;
- pre-match history but do not suppress before validation;
- do NOT perform final competition research.

Write:
state/runs/YYYY-MM-DD/merge/candidates.json
state/runs/YYYY-MM-DD/merge/status.json

Candidate fields include:
- candidate_id
- validation_index
- canonical_key
- idea_name
- core_job
- target_customer
- buyer
- product_mechanism
- triggering_article_ids
- supporting_article_ids

- after_state
- why_now
- market_gap_hypothesis
- scope_hint
- zero_cost_stack_outline
- estimated_lovable_credits
- history_match_key
- history_match_reason
- candidate_status="needs_validation"

Sort deterministically by canonical_key and assign validation_index 1..N.

Write merge/status.json with:
- status="complete"
- source_batch_index_generated_at
- feed_items_total
- feed_items_triaged
- raw_opportunity_count
- event_cluster_count
- semantic_unique_count

Initialize if absent:

==================================================
3. VALIDATE NEXT CHUNK
==================================================

Run when merge/status.json status="complete" and not all candidates are validated.

Read:
- merge/candidates.json
- validation/progress.json
- all existing validation/chunk-*.json

Validate the next MAXIMUM 5 candidates in ascending validation_index that do not
already appear in validated_candidate_ids.

For EVERY selected candidate perform the full fresh research defined in
prompts/VALIDATOR_WORKER.txt:

- re-verify triggering development/original source
- Türkiye DIRECT competitor search
- global DIRECT competitor search
- strict same-customer + same-job + substantially-same-workflow test
- adjacent competitor separation
- <=500 internal Lovable-credit feasibility
- external cash cost exactly 0
- source/evidence strength
- no rankings

Each validation result must contain the complete fields required by
prompts/VALIDATOR_WORKER.txt, including qualification_status.

Write one immutable chunk:
state/runs/YYYY-MM-DD/validation/chunk-NNN.json

Top level:
{
  "schema_version":1,
  "run_date":"YYYY-MM-DD",
  "chunk_number":N,
  "candidate_ids":[...],
  "expected_candidate_count":K,
  "validated_candidate_count":K,
  "status":"complete|incomplete",
  "results":[...],
  "completed_at":"..."
}

Only if the chunk is complete, update validation/progress.json:
- append candidate IDs
- validated_candidate_count
- next_chunk_number += 1
- status="complete" if validated_candidate_count == candidate_count else "in_progress"

Never mark candidates validated if the research was not actually completed.

Stop after this one chunk, even if more candidates remain.

==================================================
4. FINALIZE
==================================================

Run only when validation/progress.json says:
validated_candidate_count == candidate_count
and status="complete".

Hard gate:
- all 4 discovery workers complete and same frozen generation
- total triaged == source_total_items
- merge complete
- candidate_count matches candidate file
- union of complete validation chunks contains every candidate exactly once
- no candidate is missing or duplicated
- every candidate has qualification_status

If any gate fails:
write final/report.json with overall_status="RADAR_INCOMPLETE".
Do NOT update idea_history.json.
Do NOT update idea_catalog.json.
Never publish "0 ideas".
Stop.

If every gate passes:

1. Combine all validation results.
2. Compare qualified and competition_not_verified candidates semantically with
   state/idea_history.json.
3. Suppress cross-day duplicates using target customer + core job + product mechanism.
4. Surface an old idea only as a material update under the master-prompt rules.
5. Assign one exact scope_tier to each genuinely new idea:
   Lüleburgaz / Türkiye / Dünya / Evren.
6. Build full catalog records in state/idea_catalog.json schema.
7. Preserve unrelated history/catalog records.
8. Update idea_history.json and idea_catalog.json only after all validations are complete.
9. Write state/runs/YYYY-MM-DD/final/report.json with:
   - overall_status="FULL_RADAR_COMPLETE"
   - source_batch_index_generated_at
   - feed_records_total
   - feed_records_triaged
   - original_articles_verified_total
   - raw_opportunity_count
   - candidate_count
   - candidates_validated
   - new_qualified_count
   - new_competition_not_verified_count
   - duplicate_suppressed_count
   - material_update_count
   - rejected_counts_by_reason
   - emitted_new_ideas
   - competition_not_verified
   - suppressed_duplicate_keys
   - material_updates
   - completed_at

A zero-new-idea result is valid ONLY after this point.

User-facing final message:
- Turkish, simple language;
- show only NEW ideas and MATERIAL updates;
- do not repeat suppressed duplicates;
- distinguish these metrics:
  Feed records processed
  Original articles verified
  Raw opportunities generated
  Candidates competition-validated
  New qualified ideas
  New competition-not-verified ideas
  Existing duplicates suppressed
  Material updates
  Overall status

Never equate "feed records processed" with "full articles verified".


==================================================
AUTOMATION RESILIENCE — HARD RULE
==================================================
- A GitHub read/write failure must NEVER disable Discovery W1-W4 or this Orchestrator.
- For a required state path that does NOT exist, use the GitHub create-file operation.
- For a required state path that already exists, fetch its current blob SHA and use the GitHub update-file operation.
- Never call update-file without a current SHA, and never treat a create/update API error as a completed stage.
- Never report a stage as advanced unless its required state file was successfully persisted.
- On a later invocation, re-read repository state and retry the first unfinished stage.
- Never synthesize or backfill a worker from feed counts alone.
- If a frozen generation is no longer available in docs/batches/index.json, do not repair
  against a newer generation. Mark RADAR_INPUT_MISMATCH and wait for an explicit clean rerun.
